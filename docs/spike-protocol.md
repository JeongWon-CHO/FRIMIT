# 기술 스파이크 검증 절차

plan.md 5장 구현 1단계에 해당한다. **이 문서의 목적은 앱을 만드는 게 아니라, 제품이 성립하는지 재는 것**이다.
여기서 나온 숫자가 공동 풀 UX의 해상도(잔여시간을 분 단위로 보여줄지, 5분 단위로 보여줄지)를 결정한다.

## 0. 준비

### Apple Team ID — ✅ 설정됨

extension 타깃은 호스트 앱과 같은 팀으로 서명돼야 하는데, Expo의 자동 서명은 앱 타깃만 챙긴다.
그래서 `app.json`의 plugin props에 팀 ID를 직접 넣어 두었다.

```json
["./plugins/withFrimitScreenTime", { "appleTeamId": "7D75P7PR8U" }]
```

다른 팀에서 빌드할 때는 `APPLE_TEAM_ID` 환경변수로 덮어쓸 수 있다.

Team ID를 찾을 때 흔히 틀리는 지점: 인증서 이름의 괄호 안 값이 아니라 **OU 필드**가 Team ID다.

```sh
security find-certificate -c "Apple Development" -p | openssl x509 -noout -subject
# subject=UID=..., CN=Apple Development: NAME (인증서 ID), OU=팀 ID, ...
```

### Family Controls 배포 엔타이틀먼트 — ✅ 완료 (2026-08-13)

Apple 승인을 받았고, 아래 세 App ID 모두에 Family Controls (Distribution) capability를 활성화했다.
TestFlight 배포를 막을 요소는 이 항목에서 더 없다.

| 역할 | Bundle ID |
|---|---|
| 호스트 앱 | `com.frimit.app` |
| Monitor extension | `com.frimit.app.activitymonitor` |
| Notification Service extension | `com.frimit.app.notificationservice` |
| Shield Configuration extension | `com.frimit.app.shieldconfiguration` |
| ~~Report extension~~ (폐기) | ~~`com.frimit.app.activityreport`~~ |

App ID는 Xcode가 자동 서명 중에 만들고 capability까지 켜 준다. 배포 빌드는
`extra.eas.build.experimental.ios.appExtensions`에 선언된 타깃만 EAS가 프로파일을
만들어 **호스트와 같은 인증서로** 서명한다. 선언이 빠지면 extension만 개발
인증서로 서명돼 이렇게 죽는다:

```
Embedded binary is not signed with the same certificate as the parent app.
```

로컬 `expo run:ios`에서는 부모도 개발 인증서라 드러나지 않는다. 타깃을 더할 때는
`plugins/withActivityExtensions.js`의 `EXTENSIONS`만 고치면 되고, 선언과 검증
스크립트가 그 목록에서 나온다.

두 값은 `plugins/withActivityExtensions.js`가 호스트 bundle ID로부터 자동 생성하는 이름과 일치한다.
호스트 bundle ID를 바꾸면 포털의 App ID도 함께 만들어야 한다.

Report extension은 3차 측정 뒤 폐기했다(아래 기록). 포털의 `com.frimit.app.activityreport` App ID는
이제 어느 빌드에도 쓰이지 않는다 — 지워도 되고, 나중을 위해 남겨 둬도 빌드에는 영향이 없다.

## 1. 실행

Expo Go는 쓰지 않는다. 네이티브 모듈이 있으므로 development build가 필요하다.

```sh
npx expo prebuild --clean          # 네이티브 프로젝트 재생성
npx expo run:ios --device          # 실기기 선택
npx expo run:android --device
```

시뮬레이터/에뮬레이터에서는 Family Controls도 UsageStats도 실제 데이터를 주지 않는다. **반드시 실기기**.

스파이크 화면은 더 이상 앱의 첫 화면이 아니다(온보딩과 오늘 화면이 그 자리에 들어왔다).
**MY 탭 → `스파이크 화면 열기`**로 들어가거나, 개발 중이라면 `/spike`로 직접 이동한다.
계측 화면은 제품 화면과 별개로 자기 그룹을 `ensureGroup`으로 확보하므로 온보딩을 건너뛰어도 동작한다.

### 차단 (I13~I17) — ✅ 전부 통과 (2026-08-26)

측정 기록은 문서 아래에 있다. 다시 잴 때는 **I14를 I13보다 먼저** 밟는다.

| # | 확인할 것 | 기록할 값 | 왜 중요한가 |
|---|---|---|---|
| I13 | **지금 차단 (잔여 0)** 을 누른 뒤 선택한 앱을 열면 잠기는가 | 잠김/안 잠김, 걸린 시간 | ManagedSettings가 붙었는지의 증거. 여기서 막히면 아래는 전부 무의미 |
| I14 | **차단 해제**로 풀리는가 | 풀림/안 풀림 | 못 풀면 사용자를 영구히 가두는 결함이다. I13보다 중요하다 |
| I15 | 앱을 완전히 종료한 상태에서도 잠금이 유지되는가 | 유지/소실 | 잠금은 호스트 앱이 아니라 시스템이 들고 있어야 한다 |
| I16 | 차단선을 남겨 둔 채 **선택한 앱을 계속 써서** 선을 넘기면 저절로 잠기는가 | 선을 넘긴 시각, 실제로 잠긴 시각, 그 차이 | 차단의 본 경로. 차이가 임계값 그물의 간격(초반 1분, 2시간까지 5분, 그 뒤 15~30분) 안이어야 한다 |
| I17 | 기내 모드에서 I16이 그대로 되는가 | 됨/안 됨 | 네트워크에 기대지 않는다는 설계의 확인 |

I16의 차이가 그물 간격보다 훨씬 크게 나오면 `FrimitScheduler.thresholdMinutes`의
뒷부분을 촘촘히 하거나, 차단선 위치에 전용 이벤트를 하나 더 까는 쪽으로 간다.
후자는 감시를 다시 걸어야 하는데 그때 `intervalDidStart`가 즉시 불려 누적값이
0으로 돌아갈 위험이 있어 지금은 하지 않았다.

I14가 실패하면 **즉시 멈추고 고친다.** 잠금을 들고 있는 것은 앱이 아니라 시스템이라,
앱 안에서 풀지 못하면 사용자가 스스로 풀 방법이 마땅치 않다. 앱을 지웠을 때 잠금이
함께 사라지는지도 이때 함께 확인한다 — 그게 마지막 탈출구다.

I11·I12는 더 이상 측정하지 않는다. "정밀 보정" 버튼도 스파이크 화면에서 사라졌고,
`진단 정보`가 대신 계단값과 **extension이 마지막으로 기록한 시각**을 찍는다.
계단값이 멈췄을 때 "extension이 안 돈 것"과 "화면이 안 읽은 것"을 이 시각으로 구분한다.

### I6이 실패하면

임계값 이벤트가 발화하지 않는 흔한 원인들:

1. **저전력 모드** — DeviceActivity 콜백이 지연되거나 누락된다. 끄고 재시도.
2. **선택이 카테고리뿐** — 카테고리 단위 임계값은 개별 앱보다 발화가 늦다. 개별 앱을 직접 골라 재시도.
3. **이벤트가 너무 많음** — 현재 그룹당 60개를 등록한다. `FrimitScheduler.thresholdMinutes`를 5개 정도로 줄여 발화 여부만 먼저 확인.
4. **선택 저장이 extension에 안 보임** — I4로 돌아갈 것.

**A1–A6 전부 통과했다 (2026-08-18).** 아래 1·2·3차 기록에 결함 셋과 그 수정이 남아 있다.
다시 잴 일이 생긴다면 서버 쪽까지 함께 봐야 한다 — 기기 화면이 맞는데 올라간 값이 틀린
경우가 두 번 있었다.

Android는 `queryEvents`로 직접 계산하므로 **앱이 실행되는 순간 항상 정확한 값**이 나와야 한다.
오차가 크다면 `FrimitUsage.foregroundSeconds`의 이벤트 짝짓기 로직을 의심할 것.
(1차 측정에서 실제로 여기가 틀렸다. 아래 기록 참조.)

A5는 오전 6시를 실제로 넘겨야 잴 수 있다. 앱을 켜 둔 채 경계를 넘긴 뒤 새 구간의 누적을 본다.

## 4. 판단 기준

스파이크의 결론은 셋 중 하나여야 한다.

- **통과** — I6, I8이 되고 계단 해상도가 5분 이내. plan.md 그대로 진행.
- **조건부 통과** — I6은 되지만 I8(백그라운드)이 불안정. plan.md의 대비책대로 "앱 열 때 정확히 동기화, 백그라운드는 보조"로 전환한다. (원래 여기서 전략 A를 앞당기려 했지만, 전략 A 자체가 폐기됐으므로 남은 수단은 임계값 사다리를 더 촘촘히 까는 것뿐이다.)
- **실패** — I4 또는 I6이 안 됨. 공동 풀의 근거가 되는 숫자를 못 얻으므로 제품 정의를 다시 봐야 한다.

## 측정 기록

### 2026-08-13 · iPhone 14 Pro · 1차

**결론: 조건부 통과.** 전략 B(백그라운드 임계값)는 동작하고, 전략 A(정밀 보정)는 동작하지 않았다.
공동 풀 제품의 근거가 되는 숫자는 확보됐으므로 plan.md대로 진행한다.

| 항목 | 결과 | 실측값 |
|---|---|---|
| I1 권한 시트 | ✅ | — |
| I2 앱 목록 | ✅ | 인스타그램·유튜브 2개 선택 |
| I3 선택 저장 | ✅ | 앱 재시작 후에도 유지 |
| I4 App Group | ✅ | `group.com.frimit.app` |
| I5 집계 시작 | ✅ | 구간 시작 `2026-08-12T21:00:00Z` = 08-13 06:00 KST |
| **I6 누적값 상승** | **✅** | **5분 임계값 발화, 계단 300초** |
| I11 정밀 보정 | ❌ | 정밀 0초 |

#### 확인된 것

- **오전 6시 경계 계산이 실기기에서 정확했다.** `periodStartFor`가 계산한 값이 그대로 찍혔다.
- **임계값 콜백은 실제로 온다.** 백그라운드에서 iOS가 콜백 → extension이 App Group에 기록 →
  호스트가 읽기까지의 사슬 전체가 동작한다. 이것이 제품 성립의 최소 조건이었다.

#### 알아낸 iOS 동작 두 가지

1. **`AuthorizationCenter.shared.authorizationStatus`는 앱 시작 직후 신뢰할 수 없다.**
   이미 승인된 상태인데도 몇 초간 `notDetermined`로 읽히다가 뒤늦게 `approved`로 바뀐다.
   한 번 읽고 끝내면 사용자에게 "권한 없음"으로 잘못 안내하게 되므로 **구독**해야 한다.
   → `onPermissionChange` 이벤트로 대응.

2. **보이지 않는 뷰에 붙인 `DeviceActivityReport`는 실행되지 않는 것으로 보인다.**
   1×1 크기에 `alpha = 0`으로 붙였더니 정밀값이 계속 0이었다.
   → 120×120 / `alpha = 0.02`로 바꾸고, 값이 아니라 **실행 시각**의 변화를 기다리도록 수정.

### 2026-08-13 · 2차 (임계값 1분 사다리 + 계측 추가)

| 항목 | 결과 |
|---|---|
| 임계값 사다리 60개 반영 | ✅ `감시 중 1개 / 임계값 60개` |
| 계단값 누적 | ✅ 300초 → **900초(15분)**, 반복적으로 안정 발화 |
| 정밀 보정 | ❌ `report extension이 한 번도 실행되지 않음` |

**전략 B는 확정적으로 동작한다.** 임계값 콜백이 일회성이 아니라 반복해서 온다는 것까지 확인됐다.

전략 A는 뷰 크기·투명도 문제가 아니었다. 계측 덕분에 "필터가 틀렸다"가 아니라
"아예 실행되지 않는다"로 원인이 좁혀졌다. 남은 가설은 **뷰 컨트롤러 계층 구성**이다 —
`UIHostingController`의 view만 window에 얹고 `addChild`/`didMove`를 하지 않으면
SwiftUI 생명주기가 완성되지 않아, 원격 뷰 연결이 시작되지 않는 것으로 보인다.
3차에서 이것까지 안 되면 전략 A는 폐기한다.

#### 다음 측정에서 확인할 것

`정밀 보정`을 누른 뒤 기록에 아래 중 무엇이 찍히는지로 원인이 갈린다.

- `⚠️ report extension이 한 번도 실행되지 않음` → 렌더링 자체가 안 됨. 뷰를 더 키우거나,
  숨김 프로브 대신 실제 화면에 `DeviceActivityReport`를 배치하는 방식으로 바꿔야 한다.
- `report 실행됨 HH:MM:SS · 원시값 0초` → 실행은 됐고 필터가 틀렸다. `DeviceActivityFilter`의
  세그먼트(`.hourly`)와 토큰 필터 구성을 다시 봐야 한다.

**A6이 iOS만큼 중요하지 않은 이유**: Android는 스냅샷을 읽을 때마다 `queryEvents`로 구간
전체를 처음부터 다시 계산한다. 앱이 죽어 있는 동안 무엇도 놓치지 않으므로, iOS의 I8처럼
백그라운드 신뢰도가 제품 성립 조건이 되지 않는다. 대신 **계산이 틀리면 조용히 전부 틀린다** —
그게 아래에서 실제로 일어난 일이다.

#### 첫 측정에서 나온 값: 1분 사용 → 22시간 38분 41초

구간 시작 06:00에서 11시간 19분(40,760초) 지난 시점에 누적 81,521초가 찍혔다. **경과 시간의
정확히 2배**라는 것이 단서였다.

원인은 `FrimitUsage.foregroundSeconds`의 이 한 줄이었다.

```kotlin
val opened = openedAt.remove(packageName) ?: startMs
```

Android는 앱 하나를 닫을 때 `ACTIVITY_PAUSED`와 `ACTIVITY_STOPPED`를 **둘 다** 보낸다.
첫 번째에서 짝이 맞아 정상적으로 더해지고, 뒤따르는 두 번째는 짝이 없어 `?: startMs`로
떨어져 **구간 전체를 한 번 더** 더한다. "구간 시작 이전부터 켜져 있던 앱"을 위한 되돌림이
모든 짝 없는 닫힘에 적용된 것이다. 여닫은 횟수만큼 구간 전체가 반복해서 쌓인다.

고친 것 셋:

1. `startMs` 되돌림을 **이 구간에서 그 앱의 이벤트를 처음 볼 때만** 적용한다. 그 뒤의 짝 없는
   닫힘은 중복이므로 버린다.
2. 이미 열려 있는 앱에 열림이 또 오면 시작 시각을 덮어쓰지 않는다. 덮어쓰면 그 사이가 사라진다.
3. 다른 앱이 올라오거나 화면이 꺼지면 열려 있던 구간을 그 시점에 끊는다. 포그라운드는 하나뿐이다.
   닫힘 이벤트를 하나 놓쳐도 구간이 endMs까지 무한정 자라지 않는다.

3번이 없으면 이벤트 하나를 놓칠 때마다 몇 시간짜리 유령 사용량이 생긴다. 1번만 고치는 것으로는
같은 종류의 다음 사고를 막지 못한다.

#### 여기서 드러난 서버 쪽 결함

날을 위한 여유값이지 사용량의 상한이 아니다. plan.md 121행이 "서버 시간을 기준으로 기간을

이라 경계 너머까지 뻗는다.** 지키려던 마지막 몇 분과 함께 오늘 아침 네 시간이 딸려 들어왔다.

0006의 가드도 못 잡는다. 옛 구간의 상한은 구간 길이 전체(24시간)이고 16,936초는 그 안이다.
가드는 "안 흐른 시간을 썼다"를 잡지 "구간이 끝난 뒤의 시간을 썼다"는 잡지 못한다.

고친 것 둘:

1. **네이티브가 구간 끝을 안다.** `startTracking`이 `periodEnd`를 함께 받아
   `FrimitStore`에 보관하고, 스냅샷은 `min(지금, 구간 끝)`까지만 센다. 이제 순서와 무관하게
   옛 구간의 값은 경계에서 잘린다. 끝 계산은 `frimit-day.ts` 한 곳에만 두었다 — 서머타임이
   있는 시간대에서 하루는 24시간이 아니고, 그 규칙을 네이티브 두 곳에 다시 쓸 이유가 없다.
   iOS는 이 인자를 받고 버린다. `intervalDidStart`가 경계에서 구간을 스스로 넘기기 때문이다.
2. **넘긴 직후 새 구간의 첫 값을 바로 올린다.** 이 측정에서 서버에는 08-17 행이 아예 없었다.
   경계를 넘긴 뒤 앱을 닫아 버리면 다른 구성원 화면에서 그 사람은 오늘 하나도 안 쓴 것으로
   보인다. 공동 풀이 제품의 전부이므로 이건 표시 문제가 아니라 규칙이 어긋나는 문제다.

**남는 한계**: 앱이 이틀 이상 닫혀 있으면 중간 날은 영영 비어 있다. 롤오버는 저장된 구간에서
현재 구간으로 한 번에 건너뛰고, 건너뛴 날의 값을 올릴 경로가 없다. `UsageStats`에는 이벤트가
남아 있으므로 되찾는 것 자체는 가능하지만, 임의 구간을 조회하는 네이티브 API를 새로 열어야
한다. 지금은 열지 않는다.

### 2026-08-18 · Android 실기기 3차 — 경계 통과 확인, Android 항목 종료

같은 방식으로 한 번 더 오전 6시를 넘겼다. 이번에는 기기가 아니라 **서버가 어떻게 갈리는지**가
확인 대상이었다.

```
date_key 2026-08-17 · 26,894초 (7시간 28분)  seq 14
date_key 2026-08-18 ·  8,343초 (2시간 19분)  seq 2
```

스냅샷 층에 순서가 그대로 남았다.

```
23:19:15.944Z  옛 구간 08-17  seq 14  26,894   ← 마지막 값을 먼저 올리고
23:19:16.220Z  새 구간 08-18  seq  1   8,343   ← 0.28초 뒤 새 구간 첫 값
23:19:44.284Z  새 구간 08-18  seq  2   8,343   ← 다음 동기화, 값이 안 늘어 stale
```

세 가지가 한 번에 확인됐다.

1. **경계에서 잘린다.** 옛 코드였다면 08-17 칸이 26,894 + 8,343 = 35,237초가 됐을 것이다.
   2차에서 08-16 칸에 아침 네 시간이 딸려 들어간 그 경로다.
2. **끝을 모르는 값의 대체 계산이 실제로 일했다.** 기기에 저장된 08-17 구간은 이 필드가 생기기
   전 빌드가 무장한 것이라 끝이 없었고, `구간 시작 + 24시간`이 서울 기준으로 정확히
   08-18 06:00을 짚었다. 고친 빌드를 깔아도 다음 경계에서 딱 한 번 재현될 뻔한 구멍이었다.
3. **넘긴 직후의 즉시 업로드가 돈다.** 0.28초 간격의 두 업로드가 그것이다. 이게 없었다면
   08-18 칸이 비어 있고 2시간 19분은 본인 기기에만 있었을 것이다.

**Android 검증 항목(A1–A6)은 이것으로 닫는다.** 남은 것은 이틀 이상 닫아 둔 경우의 중간 날
공백뿐이고, 그건 결함이 아니라 위에 적어 둔 알려진 한계다.

### 알림으로 잠그기 (I18~I20) — ✅ 전부 통과 (2026-08-27)

남이 풀을 태워 잔여가 0이 된 경우다. 내 사용량은 1초도 늘지 않으므로 임계값
콜백이 깨어나지 않고, I13~I17의 경로로는 잡히지 않는다. "오늘 몫을 다 썼어요"
알림에 `mutable-content`를 얹어 `FrimitNotificationService`가 대신 잠근다.

**폰은 한 대면 된다.** 풀을 태우는 쪽이 할 일은 서버에 큰 누적값을 올리는 것뿐이고,
그건 Screen Time이 진짜가 아니어도 된다. 동반 계정으로 대신한다.

```sh
bash scripts/join-test-member.sh <초대코드>       # 아직 안 했다면 (참여 + 준비)
bash scripts/burn-pool.sh <초대코드> 30           # 30초 뒤에 한도를 1분 넘겨 태운다
bash scripts/reset-pool.sh <초대코드>             # 끝나면 되돌린다
```

`burn-pool.sh`는 동반 계정을 필요한 만큼 부른다. 서버가 한 사람의 누적을 그
구간에서 흐른 시간(`+900초`)까지만 받기 때문이다(0006) — 오전 10시에 8시간짜리
풀을 혼자 태우려 들면 그 규칙에 걸린다. 이른 아침일수록 계정이 더 필요하고,
오후 2시쯤부터는 한 명으로 충분하다.

`reset-pool.sh`는 동반 계정이 태운 시간과 오늘의 한도 사건을 지운다. 내 폰이
올린 사용량은 건드리지 않는다. 잠금은 기기가 들고 있어서 서버를 지운다고 풀리지
않는다 — Frimit을 한 번 열면 동기화가 잔여를 다시 알려 주고 그때 풀린다.

**지연초를 준다.** 여기서 봐야 하는 그림은 "다른 앱을 쓰고 있는데 갑자기 잠기는
것"인데, 태우자마자 발송기가 1분 안에 돌아 버려서 엔터를 치고 폰을 집어 앱을 여는
사이에 이미 끝나 있다. 30초쯤 주고 그동안 인스타그램을 열어 두면 손을 뗀 채로 볼 수
있다.

시작 후에 들어온 동반 계정은 오늘 구간의 집계 대상이 아니라(다음 오전 6시 반영,
plan.md 35행) 그대로는 `not_in_period`로 거절된다. 스크립트가 그 반영 시각만 오늘
구간 시작으로 당기고, 당겼다는 사실을 한 줄로 알린다.

다시 재기 전에 스파이크 화면에서 **`차단 해제`를 먼저 누른다.** 이미 잠겨 있으면
잠기는 순간을 볼 수 없다.

`burn-pool.sh`는 오늘의 한도 사건을 먼저 지우고 다시 만든다. 같은 사건은 그룹당
하루 한 번이라(dedupe_key) 지우지 않으면 두 번째 실행에서 알림이 아예 나가지
않는다. I19와 I20을 따로 재려면 두 번 돌려야 하므로 이게 필요하다.

내 폰의 **알림 권한이 켜져 있어야** 한다. 꺼져 있으면 이 경로 자체가 없고,
그때는 다음 동기화가 잠근다.

| # | 확인할 것 | 기록할 값 | 왜 중요한가 |
|---|---|---|---|
| I18 | 동반 계정이 한도를 다 썼을 때 내 폰에 알림이 오는가 | 옴/안 옴, 사건에서 알림까지 걸린 시간 | 발송기는 1분마다 도므로 최대 1분 + Expo 지연이 정상 |

같은 기기·같은 토큰으로 다시 받으니 정상이었으므로, 새 빌드 직후의 아이콘 캐시로
본다. 다만 **이 증상이 계속되면 의미가 다르다** — 푸시 토큰이 개발 빌드가 아니라
Expo Go에 묶여 있다는 뜻이고, 그러면 알림은 오는데 `FrimitNotificationService`는
영영 돌지 않는다. 알림은 왔는데 잠기지 않을 때 여기를 의심할 것.

확인은 콕 찌르기 한 발이 제일 빠르다. 서버에서 직접 쏠 수 있고, 잠금과 무관하게
같은 경로를 지난다.

```sh
# 동반 계정으로 로그인해 send_nudge RPC를 부르면 된다 (쿨다운 30분, 하루 10회)
```

#### 그리고 이때 결함이 하나 나왔다 — 알림이 네 개

잠기는 순간 잠금 화면에 네 줄이 한꺼번에 쌓였다.

```
우리 시간의 75%를 썼어요
우리 시간의 90%를 썼어요
오늘 몫을 다 썼어요
8분 넘겼어요
```

한도 트리거는 75·90·100을 낮은 것부터 훑고 한 번의 갱신이 세 단계를 넘기면 세
줄을 다 남긴다(0010). 활동 탭에서는 그게 맞지만, 발송기가 그대로 집어서 알림이
네 번 울렸다. 같은 묶음의 한도 사건은 가장 앞선 하나만 내보내도록 고쳤다(0023).

시각이 다르면 접히지 않는다 — 오후 2시의 75%와 저녁 8시의 100%는 다른 묶음이다.

#### 이 검증에서 만난 서버 규칙 둘

둘 다 결함이 아니라 규칙이 맞게 동작한 것이고, 스크립트가 그 사정을 몰랐다.

- `not_in_period` — 시작 후 가입자는 다음 오전 6시부터 집계 대상이다(plan.md 35행).
  `burn-pool.sh`가 동반 계정의 반영 시각만 오늘 구간 시작으로 당긴다.
- `cumulative_exceeds_period` — 한 사람의 누적은 그 구간에서 흐른 시간을 넘지
  못한다(0006). 우회하지 않고 동반 계정을 늘려 나눠 담는다.

#### 그리고 조용한 실패 하나

`reset-pool.sh`의 첫 판은 "지웠습니다"라고 말하면서 **아무것도 지우지 않았다.**
질의 문자열에 넣은 `period_start`의 `+09:00`에서 `+`가 공백으로 해석돼 조건이
어느 행에도 맞지 않았다. 성공처럼 보이는 실패라 합계를 보지 않았으면 그냥
넘어갔을 것이다. 지금은 삭제한 행 수를 찍는다.

PostgREST 질의에 타임스탬프를 넣을 때는 `+`를 `%2B`로 바꿔야 한다. 본문(JSON)으로
보낼 때는 해당 없다.

| I21 | 잠긴 앱을 열면 **그룹 이름**이 제목으로 뜨는가 | 뜬 문구 그대로 | 그룹이 여럿일 때 어느 약속 때문에 막혔는지가 이 화면 말고는 알 방법이 없다 |

한 사람이 그룹 5개까지 들어가고 겹치는 앱을 골랐다면 **그중 한 그룹의 풀만
터져도** 잠긴다 — iOS가 store들의 차단을 합집합으로 적용하기 때문이다. 나머지
그룹에 시간이 남아 있는 사람에게 기본 화면은 "왜 막혔지"만 남긴다.

그룹 이름은 `listMyGroups`가 App Group에 베껴 둔 값을 읽는다. 그룹 목록을 한
번도 읽지 않은 채 잠기면 이름이 없고, 그때는 제목이 `Frimit`으로 떨어진다.
**제목이 `Frimit`으로 나온다면 그 경로를 의심할 것** — 차단 자체는 정상이다.

"오전 6시에 다시 열려요"는 저장된 구간 시작에서 하루 뒤로 계산한다. 서머타임이
있는 시간대에서는 한 시간 어긋나지만 베타는 `Asia/Seoul` 한 곳이다.
