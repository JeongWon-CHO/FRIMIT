# 기술 스파이크 검증 절차

plan.md 5장 구현 1단계에 해당한다. **이 문서의 목적은 앱을 만드는 게 아니라, 제품이 성립하는지 재는 것**이다.
여기서 나온 숫자가 공동 풀 UX의 해상도(잔여시간을 분 단위로 보여줄지, 5분 단위로 보여줄지)를 결정한다.

## 0. 준비

### Apple Team ID — ✅ 설정됨

extension 타깃은 호스트 앱과 같은 팀으로 서명돼야 하는데, Expo의 자동 서명은 앱 타깃만 챙긴다.
그래서 `app.json`의 plugin props에 팀 ID를 직접 넣어 두었다.

```json
["./plugins/withFrimitScreenTime", { "appleTeamId": "7D75P7PR8U" }]
```

다른 팀에서 빌드할 때는 `APPLE_TEAM_ID` 환경변수로 덮어쓸 수 있다.

Team ID를 찾을 때 흔히 틀리는 지점: 인증서 이름의 괄호 안 값이 아니라 **OU 필드**가 Team ID다.

```sh
security find-certificate -c "Apple Development" -p | openssl x509 -noout -subject
# subject=UID=..., CN=Apple Development: NAME (인증서 ID), OU=팀 ID, ...
```

### Family Controls 배포 엔타이틀먼트 — ✅ 완료 (2026-08-13)

Apple 승인을 받았고, 아래 세 App ID 모두에 Family Controls (Distribution) capability를 활성화했다.
TestFlight 배포를 막을 요소는 이 항목에서 더 없다.

| 역할 | Bundle ID |
|---|---|
| 호스트 앱 | `com.frimit.app` |
| Monitor extension | `com.frimit.app.activitymonitor` |
| ~~Report extension~~ (폐기) | ~~`com.frimit.app.activityreport`~~ |

두 값은 `plugins/withActivityExtensions.js`가 호스트 bundle ID로부터 자동 생성하는 이름과 일치한다.
호스트 bundle ID를 바꾸면 포털의 App ID도 함께 만들어야 한다.

Report extension은 3차 측정 뒤 폐기했다(아래 기록). 포털의 `com.frimit.app.activityreport` App ID는
이제 어느 빌드에도 쓰이지 않는다 — 지워도 되고, 나중을 위해 남겨 둬도 빌드에는 영향이 없다.

## 1. 실행

Expo Go는 쓰지 않는다. 네이티브 모듈이 있으므로 development build가 필요하다.

```sh
npx expo prebuild --clean          # 네이티브 프로젝트 재생성
npx expo run:ios --device          # 실기기 선택
npx expo run:android --device
```

시뮬레이터/에뮬레이터에서는 Family Controls도 UsageStats도 실제 데이터를 주지 않는다. **반드시 실기기**.

## 2. iOS 검증 항목

앱의 스파이크 화면에서 1→2→3 순서대로 누르고 아래를 기록한다.

| # | 확인할 것 | 기록할 값 | 왜 중요한가 |
|---|---|---|---|
| I1 | 권한 요청 시트가 뜨는가 | 뜸/안 뜸, 오류 메시지 | entitlement가 제대로 붙었는지의 증거 |
| I2 | `FamilyActivityPicker`에 앱 목록이 나오는가 | 나옴/빈 목록 | 권한이 실제로 승인됐는지 |
| I3 | 선택 후 개수가 저장되는가 | 선택 개수 | 앱을 껐다 켜도 유지되는지 함께 확인 |
| I4 | 진단의 **App Group 연결** | 연결됨/안 됨 | ❗️안 되면 extension이 값을 못 넘긴다. 여기서 막히면 아래는 전부 무의미 |
| I5 | 집계 시작이 오류 없이 되는가 | 성공/실패 사유 | 동시 감시 20개 한계도 함께 확인 |

| I8 | 앱을 완전히 종료한 뒤에도 누적이 이어지는가 | 종료 전/후 값 | 백그라운드 신뢰도. plan.md 175행의 판단 근거 |
| I9 | 기기 재부팅 후에도 감시가 살아있는가 | 유지/소실 | 소실되면 앱 실행 시 재등록 로직이 필요 |
| I10 | 오전 6시 경계에서 누적값이 0으로 돌아가는가 | 경계 전후 값 | 하루 경계 처리의 실측. 기기 시각을 조작하지 말고 실제로 넘겨서 확인 |
| ~~I11~~ | ~~**정밀 보정**을 눌렀을 때 값이 갱신되는가~~ | — | 전략 A와 함께 폐기 (3차 기록 참조) |
| ~~I12~~ | ~~정밀 보정에 걸리는 시간~~ | — | 위와 같음 |

I11·I12는 더 이상 측정하지 않는다. "정밀 보정" 버튼도 스파이크 화면에서 사라졌고,
`진단 정보`가 대신 계단값과 **extension이 마지막으로 기록한 시각**을 찍는다.
계단값이 멈췄을 때 "extension이 안 돈 것"과 "화면이 안 읽은 것"을 이 시각으로 구분한다.

### I6이 실패하면

임계값 이벤트가 발화하지 않는 흔한 원인들:

1. **저전력 모드** — DeviceActivity 콜백이 지연되거나 누락된다. 끄고 재시도.
2. **선택이 카테고리뿐** — 카테고리 단위 임계값은 개별 앱보다 발화가 늦다. 개별 앱을 직접 골라 재시도.
3. **이벤트가 너무 많음** — 현재 그룹당 60개를 등록한다. `FrimitScheduler.thresholdMinutes`를 5개 정도로 줄여 발화 여부만 먼저 확인.
4. **선택 저장이 extension에 안 보임** — I4로 돌아갈 것.

## 3. Android 검증 항목

| # | 확인할 것 | 기록할 값 |
|---|---|---|
| A1 | Usage Access 설정 화면이 열리는가 | 열림/안 열림 |
| A2 | 설정에서 켠 뒤 앱으로 돌아왔을 때 권한이 `granted`로 바뀌는가 | 바뀜/안 바뀜 |
| A3 | 설치 앱 목록이 나오는가 | 앱 개수 |
| A4 | 앱을 사용한 뒤 누적값이 오르는가 | 실제 사용 시간 vs 표시된 값의 차이 |
| A5 | 구간 시작 이전부터 켜져 있던 앱이 정확히 잘리는가 | 오차(초) |
| A6 | 앱 종료 후에도 값이 유지되는가 | 유지/소실 |

Android는 `queryEvents`로 직접 계산하므로 **앱이 실행되는 순간 항상 정확한 값**이 나와야 한다.
오차가 크다면 `FrimitUsage.foregroundSeconds`의 이벤트 짝짓기 로직을 의심할 것.

## 4. 판단 기준

스파이크의 결론은 셋 중 하나여야 한다.

- **통과** — I6, I8이 되고 계단 해상도가 5분 이내. plan.md 그대로 진행.
- **조건부 통과** — I6은 되지만 I8(백그라운드)이 불안정. plan.md의 대비책대로 "앱 열 때 정확히 동기화, 백그라운드는 보조"로 전환한다. (원래 여기서 전략 A를 앞당기려 했지만, 전략 A 자체가 폐기됐으므로 남은 수단은 임계값 사다리를 더 촘촘히 까는 것뿐이다.)
- **실패** — I4 또는 I6이 안 됨. 공동 풀의 근거가 되는 숫자를 못 얻으므로 제품 정의를 다시 봐야 한다.

## 측정 기록

### 2026-08-13 · iPhone 14 Pro · 1차

**결론: 조건부 통과.** 전략 B(백그라운드 임계값)는 동작하고, 전략 A(정밀 보정)는 동작하지 않았다.
공동 풀 제품의 근거가 되는 숫자는 확보됐으므로 plan.md대로 진행한다.

| 항목 | 결과 | 실측값 |
|---|---|---|
| I1 권한 시트 | ✅ | — |
| I2 앱 목록 | ✅ | 인스타그램·유튜브 2개 선택 |
| I3 선택 저장 | ✅ | 앱 재시작 후에도 유지 |
| I4 App Group | ✅ | `group.com.frimit.app` |
| I5 집계 시작 | ✅ | 구간 시작 `2026-08-12T21:00:00Z` = 08-13 06:00 KST |
| **I6 누적값 상승** | **✅** | **5분 임계값 발화, 계단 300초** |
| I11 정밀 보정 | ❌ | 정밀 0초 |

#### 확인된 것

- **오전 6시 경계 계산이 실기기에서 정확했다.** `periodStartFor`가 계산한 값이 그대로 찍혔다.
- **임계값 콜백은 실제로 온다.** 백그라운드에서 iOS가 콜백 → extension이 App Group에 기록 →
  호스트가 읽기까지의 사슬 전체가 동작한다. 이것이 제품 성립의 최소 조건이었다.

#### 알아낸 iOS 동작 두 가지

1. **`AuthorizationCenter.shared.authorizationStatus`는 앱 시작 직후 신뢰할 수 없다.**
   이미 승인된 상태인데도 몇 초간 `notDetermined`로 읽히다가 뒤늦게 `approved`로 바뀐다.
   한 번 읽고 끝내면 사용자에게 "권한 없음"으로 잘못 안내하게 되므로 **구독**해야 한다.
   → `onPermissionChange` 이벤트로 대응.

2. **보이지 않는 뷰에 붙인 `DeviceActivityReport`는 실행되지 않는 것으로 보인다.**
   1×1 크기에 `alpha = 0`으로 붙였더니 정밀값이 계속 0이었다.
   → 120×120 / `alpha = 0.02`로 바꾸고, 값이 아니라 **실행 시각**의 변화를 기다리도록 수정.

### 2026-08-13 · 2차 (임계값 1분 사다리 + 계측 추가)

| 항목 | 결과 |
|---|---|
| 임계값 사다리 60개 반영 | ✅ `감시 중 1개 / 임계값 60개` |
| 계단값 누적 | ✅ 300초 → **900초(15분)**, 반복적으로 안정 발화 |
| 정밀 보정 | ❌ `report extension이 한 번도 실행되지 않음` |

**전략 B는 확정적으로 동작한다.** 임계값 콜백이 일회성이 아니라 반복해서 온다는 것까지 확인됐다.

전략 A는 뷰 크기·투명도 문제가 아니었다. 계측 덕분에 "필터가 틀렸다"가 아니라
"아예 실행되지 않는다"로 원인이 좁혀졌다. 남은 가설은 **뷰 컨트롤러 계층 구성**이다 —
`UIHostingController`의 view만 window에 얹고 `addChild`/`didMove`를 하지 않으면
SwiftUI 생명주기가 완성되지 않아, 원격 뷰 연결이 시작되지 않는 것으로 보인다.
3차에서 이것까지 안 되면 전략 A는 폐기한다.

#### 다음 측정에서 확인할 것

`정밀 보정`을 누른 뒤 기록에 아래 중 무엇이 찍히는지로 원인이 갈린다.

- `⚠️ report extension이 한 번도 실행되지 않음` → 렌더링 자체가 안 됨. 뷰를 더 키우거나,
  숨김 프로브 대신 실제 화면에 `DeviceActivityReport`를 배치하는 방식으로 바꿔야 한다.
- `report 실행됨 HH:MM:SS · 원시값 0초` → 실행은 됐고 필터가 틀렸다. `DeviceActivityFilter`의
  세그먼트(`.hourly`)와 토큰 필터 구성을 다시 봐야 한다.

전략 A가 끝내 안 되더라도 제품은 성립한다. 그 경우 이 타깃을 제거하면 심사 리스크도 함께 사라진다.

### 2026-08-13 · 3차 (뷰 컨트롤러 계층 구성 후) — 전략 A 폐기

| 항목 | 결과 |
|---|---|
| 계단값 누적 | ✅ **900초(15분)**까지 누적, 1분 사다리로 반복 발화 |
| 정밀 보정 | ❌ `report extension이 한 번도 실행되지 않음` |

2차에서 남겨 둔 마지막 가설(`addChild`/`didMove`로 SwiftUI 생명주기를 완성한다)까지 적용했지만
`reportLastRunAt`은 끝내 `null`이었다. 세 번의 측정에서 바꿔 본 것은 다음과 같다.

| 차수 | 바꾼 것 | 결과 |
|---|---|---|
| 1차 | 1×1 / `alpha = 0` 숨김 뷰 | 실행 안 됨 |
| 2차 | 120×120 / `alpha = 0.02`, 실행 시각 계측 추가 | 실행 안 됨 (원인이 "필터"가 아니라 "미실행"임을 확인) |
| 3차 | `addChild` + `didMove`로 뷰 컨트롤러 계층 구성 | 실행 안 됨 |

**결론: 전략 A 폐기.** 2차에서 정한 기준("3차에서 이것까지 안 되면 폐기") 그대로다.
남은 선택지는 화면에 실제로 보이는 `DeviceActivityReport`를 배치하는 것뿐인데, 그건
"숫자만 조용히 얻는다"는 원래 목적과 다른 UI를 제품에 강제한다. 게다가 이 경로에는
심사 리스크가 붙어 있었으므로, 얻는 것보다 지고 가는 것이 크다.

#### 제거한 것 (2026-08-13)

- `FrimitActivityReport` 타깃 — config plugin의 `EXTENSIONS`에서 제외. 이미 만들어진
  프로젝트에서도 소스가 지워지도록 `RETIRED_EXTENSIONS`로 남겨 두었다.
- `plugins/extensions/report/`, `modules/screen-time/ios/FrimitReportProbe.swift`
- App Group의 report 관련 키 전부 (`frimit.usage.report.*`, `pendingReportGroup`, 계측 키 2개)
- JS API `refreshReport`, `getUsageBreakdown` → 임계값 경로만 보는 `getUsageDetail`로 대체

`npm run verify:prebuild`가 이제 이 타깃이 **되살아나지 않는 것까지** 확인한다.

#### 이후 정확도를 올려야 한다면

정밀 합계라는 선택지가 사라졌으므로 해상도는 임계값 사다리가 전부다. 올릴 방법은 둘뿐이다.

1. `FrimitScheduler.thresholdMinutes`의 앞 구간을 더 촘촘히 (1분 → 30초 단위는 불가, 최소 단위가 분이다)
2. 이벤트 개수를 늘리기 — 현재 60개. 늘렸을 때 발화 신뢰도가 떨어지는지는 다시 측정해야 한다.
